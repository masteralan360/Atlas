# Atlas for Windows · Hybrid performance and POS checkout investigation

- **Incident date** 25 November 2026, Asia/Baghdad (UTC+03:00)
- **Affected builds identified** v0.19.2 and v0.19.7
- **Scope** Read-only analysis of the supplied WebView2 archive and desktop error log, the corresponding release tags, and the v0.19.9 checkout. Identifiers in this report are shortened.

## 1. Executive summary

**The strongest explanation for the POS failure is a failed November 22 cash sale that kept later checkouts on the local stock-planning path after the device could reach Supabase again.** Atlas treats any workspace `stock_operations` row outside `synced` or `discarded` as a reason to use that path. The recovered outbox contains exactly one such row, a failed cash checkout with a matching conflicted local sale and cash payment. v0.19.7 introduced a separate per-product, per-storage stock-source baseline that local planning requires. The recovered database contains **706 aggregate reservation baselines and zero stock-source baselines**. With that combination, a successful live reservation check can be followed by the exact offline preparation error before the checkout commit RPC is called. This is a confirmed code behavior and a **high-confidence explanation** for the v0.19.7 incident. The log has no attempt IDs or call stacks on the toasts, so individual attempts cannot all be assigned to a branch.

**Slow startup had a directly observed remote failure component and a separate, measurable-at-the-storage-layer source of local I/O.** The log records two explicit eight-second auth timeout episodes, a startup hydration burst whose failed requests completed in approximately seven-second waves, and thousands of repeated background fetch failures. The WebView2 archive also records two local IndexedDB write bursts, with 40 successful LevelDB flushes in each and three explicit memtable waits across both. The Hybrid startup path reads the SQLite workspace mirror, parses its rows, clears the corresponding Dexie rows and writes them back. That path is a strong candidate for the write bursts and for additional load, although the archive contains no per-phase timing or native Atlas SQLite copy to attribute the total delay.

**The dual reset removed state sufficient to keep checkout blocked and changed several other conditions at once.** Both stores can hold the outbox. Clearing both prevents the mirror from immediately restoring the failed checkout or the existing Dexie cache from reseeding it into a new mirror. Relaunch also replaced the browser session and reran online hydration. Physical corruption, the specific network fault and the effectiveness of a single-store reset remain unverified. The historical failed cash sale and payment merit read-only reconciliation against the server before any decision to re-record them.

## 5. Relationship and cleanup

The symptoms share a **degraded Hybrid session**, with two different mechanisms. Transport failures and retry work delayed auth/hydration and reduced opportunities to prepare stock. A persisted failed checkout then selected a local planner through an independent business rule. That planner could fail even when the network and aggregate reservation RPC worked. Heavy SQLite-to-Dexie restoration can add to startup work and can reintroduce the failed row during recovery. The evidence cannot show that a slow startup itself caused that November 22 replay rejection, or that performance delay alone produced the November 25 toasts.

The archive contains evidence of a logical browser-data clear. The final `MANIFEST-006653` references only `011424.ldb` (330 bytes) and the current `011416.log` (48 bytes). There is no live AtlasDatabase metadata in that set. The older files preserve its metadata and data. In the Local Storage keyspace for `http://tauri.localhost`, the latest archive entries have no live keys across 321 observed keys, with 195 prior value versions recoverable by key. These include a persisted Supabase auth entry, session recovery, workspace cache, mode and freshness data. The recovered last-sync timestamp is 16:55:16.657. It is a UI sync marker and cannot certify that the failed row cleared. Settings navigation followed by root, IndexedDB deletion and localStorage tombstones fits the application’s `handleConfirmClearAllData`, which deletes Dexie and clears web storage before reloading. No action event establishes who triggered that clear or its exact relationship to the reported filesystem deletion. [Settings clear flow](<E:/ERP System/Atlas/src/ui/pages/Settings.tsx:1204>) · [Last-sync marker](<E:/ERP System/Atlas/src/sync/useSyncStatus.ts:97>)

## 6. Additional findings

- **Availability cache lifetime and scope.** Both writers store `confirmedAt`. Offline validation checks structure and values and accepts rows regardless of age. Cache keys include actor and order exclusion, while local planning can read baselines outside the permission refresh cycle. There is also a gap between query loading, submit-time aggregate preflight and source planning. A request canceled before response leaves the baseline at its previous state. [Aggregate baseline](<E:/ERP System/Atlas/src/local-db/offlineStockAvailability.ts:10>) · [Source reader and writer](<E:/ERP System/Atlas/src/local-db/stockBatches.ts:725>)
- **The checkout toast hides the outbox blocker.** The app can continue to show an online session while stock actions inherit a workspace-wide ordering constraint. The user gets a preparation instruction even when an old cash reconciliation is the gate. Sync markers and connectivity labels are insufficient to indicate write eligibility.
- **Payment ambiguity is recoverable by stable ID.** A transport error can occur following an accepted server write. Preserve the original operation and reconcile by its sale ID. Generating a replacement ID after a blind reset or retry risks another sale and payment. The current client uses a stable ID within its checkout retry flow. The report found no corresponding server outcome for the historical failed command.
